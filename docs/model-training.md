# Model Training

This document is the full, honest record of how `weights.json` was produced.
Nothing in this file is illustrative or hypothetical — every number here was
printed by an actual run of `tools/ChurnTrainer.java` against
`sample-data/customers.csv`.

## Data

900 synthetic customer rows, generated by `tools/ChurnDataGen.java` from a
known logistic ground-truth process (so the "true" feature effects are
known and the trained model's recovered weights can be sanity-checked
against them) plus genuine sampling noise (churn labels are drawn as
Bernoulli samples from the true probability, not thresholded — so the
problem is realistically noisy, not perfectly separable).

- 900 total rows, 122 churned (13.6%)
- Split 80/20 (720 train / 180 test), deterministic by row index

**This is synthetic data.** No real customer, order or subscription data
was used or seen by this project.

## Training configuration

| Parameter | Value |
|---|---|
| Algorithm | Logistic regression, batch gradient descent |
| Epochs | 4,000 |
| Learning rate | 0.15 |
| L2 regularization (λ) | 0.002 |
| Feature scaling | Standardization (mean/std from the training set only) |
| Class weighting | Positive class weighted ×6.3469 (≈ train negatives / train positives) |

## Results: unweighted vs. class-weighted

Both runs used identical data, split, features and hyperparameters — the
only difference is class weighting.

| Metric | Unweighted | Class-weighted (shipped) |
|---|---|---|
| Test accuracy | 91.7% | 73.3% |
| Baseline accuracy (always predict "no churn") | 86.7% | 86.7% |
| Test precision | 100.0% | 32.4% |
| Test recall | 37.5% | 91.7% |
| Test F1 | 0.546 | 0.478 |
| Confusion matrix (TP/FP/TN/FN) | 9 / 0 / 156 / 15 | 22 / 46 / 110 / 2 |

**Read this table carefully — the unweighted model's higher accuracy is not
the same as it being the better model for this task.** It reaches 91.7%
accuracy largely by predicting "no churn" for almost everyone, which is
already correct 86.7% of the time on this imbalanced data; it only ever
flags a customer as churn-risk when very confident, catching just 9 of the
24 actual churners in the test set. The class-weighted model gives up
precision to catch 22 of those 24 — 46 false alarms in 180 customers, but 2
missed churners instead of 15.

**This project ships the class-weighted model** on the judgment that, for a
churn tool feeding a retention workflow, missing churners is usually more
costly than reviewing some false positives — but that judgment belongs to
whoever deploys this, not to this model. See `docs/design-decisions.md` for
the fuller discussion, and consider exposing the classification threshold
directly (Future Enhancements in the README) rather than treating this
choice as fixed.

## Recovered feature weights (shipped, class-weighted model)

| Feature | Weight (standardized) | Sign matches the data-generating process? |
|---|---|---|
| tenure_months | -0.5407 | Yes (longer tenure → lower churn) |
| monthly_spend | -0.5361 | Yes (higher spend → lower churn) |
| support_tickets_last_90d | +0.2736 | Yes (more tickets → higher churn) |
| days_since_last_order | +0.9097 | Yes (longer gap → higher churn) — strongest signal |
| discount_usage_rate | +0.1496 | Yes, but weaker than the generating process implied |
| nps_score | -0.6952 | Yes (higher satisfaction → lower churn) — second-strongest |
| is_subscribed | -0.0091 | Yes in sign, but the signal is essentially noise-level |

`is_subscribed`'s weak recovered weight and `discount_usage_rate`'s
weaker-than-expected one are both discussed candidly in
`docs/design-decisions.md` rather than omitted.

## Reproducing this

```bash
cd tools
java ChurnDataGen.java    # writes customers.csv (optional — one is already committed)
java ChurnTrainer.java    # trains, evaluates, writes weights.json, prints this table
```

Both are single Java files with no dependencies beyond the JDK (21+) — no
Maven build is needed to run them.
